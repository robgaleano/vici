## 2. Deferred Items

### 2.1 Community of Madrid pre-seed (~18,000 H3 resolution-9 hexagons)

**What it is:** A one-time bulk insert of all H3 resolution-9 hexagons covering the entire Community of Madrid into the `zones` table, with corresponding `zone_scores` rows (score = 0) for all 3 active teams per zone.

**Why it was deferred:** Requires a dedicated script or Edge Function to compute ~18,000 `h3_index` values, generate PostGIS geometry, and bulk-insert without exceeding DB limits. The schema is fully ready; execution was separated from the schema task.

**Decisions already made:**

- Scope: **entire Community of Madrid**, not just the city of Madrid. Testers in outskirts must be playable from day one.
- Resolution: H3 `resolution 9` (agreed in decision #16).
- Tool: `h3-js` in the script layer — h3-pg is not available on free tier.
- Format per zone row: `h3_index` (text), `boundary geometry(Polygon,4326)`, `centroid geometry(Point,4326)`, `owner_team_id = null`.
- `zone_scores` rows: one per team per zone at `score = 0` — 3 × 18,000 = ~54,000 rows.
- Zones with no activity appear neutral on the map — expected, correct behavior.

**Which task should pick it up:** Epic 03 — Maps & Geolocation (task 3.x). Alternatively, a standalone DevOps/data task before the first beta build. It does not block auth, onboarding, or the activity recording flow.

**Prerequisite to start:** A Node script (or Edge Function) that iterates H3 cells at res-9 covering the Community of Madrid bounding polygon, generates `ST_GeomFromText` for each cell, and inserts via the Supabase service-role key. The `zones` and `zone_scores` tables and their RLS policies are already in place.

### 2.2 Auth providers setup (Apple Sign-In, Google OAuth, email/password)

**What it is:** Configuring the three agreed authentication methods in the Supabase Dashboard and wiring them into the mobile app.

**Why it was deferred:** Auth provider configuration involves App Store/Google Play credentials (app IDs, secrets, redirect URLs) and belongs to the auth epic, not the schema task.

**Decisions already made:**

- Methods: **Apple Sign-In + Google OAuth + email/password** (closed in session 2026-04-29).
- Apple Sign-In is **mandatory** under App Store rules once any social login is offered on iOS.
- Magic link and other providers are out of scope for v1.
- Email lives only in `auth.users` — never duplicated in `public.profiles`.
- Profile bootstrap trigger is already in place: `handle_new_user` auto-creates a `profiles` row on every `auth.users` insert, so provider choice does not affect the profile initialization path.

**Which task should pick it up:** Task 2.x — Auth & Security (Epic 02).

**Prerequisite to start:** Apple Developer account with Sign In with Apple capability configured; Google Cloud project with OAuth 2.0 credentials for the Expo app bundle IDs.

### 2.3 End-to-end flow verification (sign-up → onboarding → activity → wallet)

**What it is:** A manual or automated test pass confirming the full player lifecycle works: user signs up → profile is created → onboarding sets `username` and `team_id` → an activity is recorded and validated → `wallet_balance` is credited.

**Why it was deferred:** Cannot be verified until auth providers are live and the onboarding screens exist (task 2.x).

**Decisions already made:**

- The profile bootstrap trigger (`handle_new_user`) is already applied — profile row creation is automatic.
- `username` and `team_id` start as `null`, non-null only after onboarding. The app must gate the main flow on `onboarding_completed_at IS NOT NULL`.
- Wallet credit mechanism: `activity_reward` transaction inserted by the Edge Function that validates each activity. Formula: `wallet_credits = round(valid_distance_km * 10)`. Invalid activity = 0 credits.
- `profiles.wallet_balance` is a materialized balance — must stay in sync with the `transactions` ledger through backend logic (never client-side).
- The client never writes to `transactions` or transitions `activities.validation_status` directly.

**Which task should pick it up:** Task 2.x (auth wiring) followed by Task 4.x (gameplay/running loop). The full chain can only be verified once all three pieces are assembled.

## 4. Pick Up Here — Brief for the Next Agent

### Immediate next task: Task 2.x — Auth & Security (Epic 02)

The schema is complete and live. The Supabase client is wired into the mobile app. What is missing is:

1. **Auth providers in Supabase Dashboard**: enable Apple Sign-In, Google OAuth, and email/password under Authentication → Providers.
2. **Mobile app auth screens**: the `app/(auth)/` directory already exists with stub files (`login.tsx`, `register.tsx`, `forgot-password.tsx`). Wire these to the Supabase Auth API using the existing typed client at `apps/mobile/lib/supabase/client.ts`.
3. **Onboarding gate**: after sign-up/sign-in, check `profiles.onboarding_completed_at`. If null, redirect to an onboarding screen that captures `username` (globally unique, case-insensitive) and `team_id`. Write these to `profiles` via `supabase.from('profiles').update(...)`.
4. **Session persistence**: `autoRefreshToken` and `persistSession` are already set to `true` in the client. Add a session listener in the root layout (`_layout.tsx`) to redirect users based on auth + onboarding state.

### After task 2.x: Madrid pre-seed (can be parallelized)

Write a Node script that:

1. Uses `h3-js` to enumerate all H3 resolution-9 cells within the Community of Madrid bounding polygon.
2. For each cell: computes boundary (hexagonal polygon) and centroid using `h3-js` cell-to-boundary / center APIs, converts to WKT `POLYGON` / `POINT` strings.
3. Bulk-inserts into `zones` using the Supabase service-role key (never the anon key for backend writes).
4. For each inserted zone, inserts 3 `zone_scores` rows (one per active team, `score = 0`).

The service-role key is available in the Supabase Dashboard under Project Settings → API. **Do not commit it.** Pass as an env variable.

### Key invariants to preserve

- `activities.validation_status` is only set by backend logic (Edge Function / RPC). Never `UPDATE` it from the client.
- `transactions` inserts are backend-only. The client reads its own rows but never creates them.
- `zones` and `zone_scores` writes are backend-only (the RLS policies enforce this).
- `profiles.wallet_balance` must stay consistent with the `transactions` ledger — keep both in sync inside the same atomic backend operation.
- PostGIS geometry uses `extensions.geometry(...)` qualified type because PostGIS was installed into the `extensions` schema.
