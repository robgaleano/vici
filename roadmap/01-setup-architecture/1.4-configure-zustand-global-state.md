## Objective

Set up Zustand as VICI's client-side state management layer. Define the stores that will power auth session handling, game state, and the active running session — with the right typing, persistence strategy, and separation of concerns so future epics can plug in without rearchitecting.

## Decisions Made

### D1 — Store location: `apps/mobile/lib/store/`

**Decision:** stores live in `apps/mobile/lib/store/`, one file per store, with an `index.ts` barrel export.

**Why:** co-located with the app that owns them, consistent with how the rest of `lib/` is structured (`supabase/`, `types/`, `utils/`). Avoids prematurely moving state management into a shared package before there are multiple apps consuming it.

**Future note:** if a second app (e.g. admin panel) ever needs to share a store, extract it to `packages/shared/` at that point — not before.

---

### D2 — `useAuthStore` holds auth only (not profile)

**Decision:** `useAuthStore` is scoped to the Supabase session and `User` object. The product profile (`username`, `team_id`, `wallet_balance`, `onboarding_completed_at`) belongs to a separate `useProfileStore` (or a lightweight `useProfile` hook, decided in task 2.x).

**Why:** mirrors the DB-level separation we deliberately designed in task 1.3 (`auth.users` vs `public.profiles`). Mixing them in one store would couple auth state changes to profile re-fetches and create a single point of failure.

**Future note:** `useProfileStore` is deferred to task 2.x because its shape depends on the onboarding flow being defined. At that point, wire it to read from `profiles` after `initialize()` resolves.

---

### D3 — `useAuthStore` has three actions: `initialize`, `login`, `logout`

**Decision:** three actions, not two.

| Action         | Responsibility                                                                                                                                               |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `initialize()` | Called once on app mount in root `_layout.tsx`. Calls `supabase.auth.getSession()` and subscribes to `onAuthStateChange`. Sets `isLoading: false` when done. |
| `login()`      | Triggers a sign-in flow (provider TBD in Epic 02). Updates `session` and `user` in store.                                                                    |
| `logout()`     | Calls `supabase.auth.signOut()`, clears `session` and `user`.                                                                                                |

**Why:** without `initialize()`, the app flashes to the login screen on every cold start while the stored session is being read from SecureStore. `isLoading: true` during init is the gate that prevents premature redirects.

**Future note (Epic 02):** `login()` will need to handle at least three providers (Apple, Google, email/password). The action signature should accept a `provider` discriminated union so each path is typed — design that when auth screens are built.

---

### D4 — Session persisted to `expo-secure-store`, not AsyncStorage

**Decision:** use `expo-secure-store` as the custom storage adapter passed to `createClient`. Do not use `@react-native-async-storage/async-storage` for the JWT.

**Why:** the Supabase session token is a bearer credential — it grants full API access for its lifetime. Storing it unencrypted violates OWASP M9 (Insecure Data Storage for mobile). `expo-secure-store` writes to the device's Keychain (iOS) / Keystore (Android), encrypted at rest and inaccessible to other apps.

**Implementation:** wrap `SecureStore.getItemAsync`, `SecureStore.setItemAsync`, and `SecureStore.deleteItemAsync` into a ~10-line adapter object and pass it as `storage` in `createClient`'s `auth` options. This replaces the default `localStorage`-based adapter that doesn't work in React Native anyway.

**Future note:** `expo-secure-store` has a per-item size limit (~2 KB on iOS). The Supabase session JSON is typically well under this limit, but if it ever grows (e.g. large JWT custom claims), split the storage across multiple keys.

### D5 — `useGameStore` is a typed skeleton in task 1.4

**Decision:** define `useGameStore` with the agreed fields typed correctly, all initialised to empty/null. No fetching logic. No real data. The skeleton locks the type contract so future tasks have a known integration point.

**Fields to type now (shape only):**

| Field               | Type               | Populated by              |
| ------------------- | ------------------ | ------------------------- |
| `nearbyZones`       | `ZoneWithScores[]` | Epic 03 (Maps)            |
| `currentTeam`       | `Team \| null`     | Epic 02 (Auth/onboarding) |
| `competitivePoints` | `number`           | Epic 04 (Gameplay)        |

**Why:** building real logic before the underlying features exist creates throwaway work. The value now is the type contract, not the implementation.

**Future note (Epic 03):** `nearbyZones` will be populated by a map viewport query against the `zones_with_scores` view. The fetch belongs in a `loadNearbyZones(viewport)` action added to the store at that point.

**Future note (Epic 02):** `currentTeam` should be derived from `useProfileStore` once the profile is loaded after onboarding, not fetched independently.

---

### D6 — `useActivityStore` is a full in-flight session accumulator

**Decision:** `useActivityStore` holds the full state of an in-progress running session.

**Shape:**

| Field              | Type                             | Purpose                                                        |
| ------------------ | -------------------------------- | -------------------------------------------------------------- |
| `status`           | `'idle' \| 'active' \| 'paused'` | drives UI and action guards                                    |
| `startedAt`        | `string \| null`                 | ISO timestamp, set when session begins                         |
| `distanceKm`       | `number`                         | running total, updated as GPS points arrive                    |
| `durationSeconds`  | `number`                         | elapsed time                                                   |
| `routeCoordinates` | `Coordinate[]`                   | growing array of GPS points for route building                 |
| `gpsPointCount`    | `number`                         | mirrors `routeCoordinates.length`, used for anti-cheat summary |

**Actions (skeleton for now, logic in Epic 04):**

| Action                 | Responsibility                                                     |
| ---------------------- | ------------------------------------------------------------------ |
| `startSession()`       | sets `status: 'active'`, records `startedAt`                       |
| `addCoordinate(coord)` | appends to `routeCoordinates`, increments counters                 |
| `pauseSession()`       | sets `status: 'paused'`                                            |
| `resumeSession()`      | sets `status: 'active'`                                            |
| `endSession()`         | sets `status: 'idle'`, returns snapshot for DB write, resets state |

**Why:** the store is the source of truth for the in-flight session. `routeCoordinates` must accumulate here so the periodic ~1 km DB flush (from the agreed task 1.3 write flow) has data to send. The simplified route submitted to the DB is derived from this array at flush time.

**Future note (Epic 04):** `addCoordinate` is where GPS validation (teleport detection, speed checks) will be enforced before appending. The `endSession()` snapshot is what gets sent to the Edge Function for final validation.

---

### D7 — Include `immer` middleware

**Decision:** install `immer` and use the Zustand `immer` middleware wrapper on stores that benefit from mutable update syntax.

**Why:** `useActivityStore` appends a GPS coordinate on every location tick. Without immer, every `addCoordinate` call allocates a new array via spread (`[...state.routeCoordinates, coord]`). With immer, it becomes `state.routeCoordinates.push(coord)` — cleaner, no allocation per tick, and the correct pattern when dealing with frequently mutated arrays.

**Scope:** apply immer middleware only to `useActivityStore` where it earns its keep. `useAuthStore` and `useGameStore` are flat enough that spread is fine — but the pattern is established and ready to extend.

**Future note:** immer is also the right tool if `useGameStore` ever holds nested zone state that needs partial updates without full object replacement.

---

### D8 — `StateCreator<T>` used on all stores

**Decision:** every store is defined using the `StateCreator<T>` pattern, not the inline `create<T>((set) => ...)` shorthand.

**Pattern:**

```ts
type AuthState = { ... }
const authSlice: StateCreator<AuthState> = (set) => ({ ... })
const useAuthStore = create<AuthState>()(authSlice)
```

**Why:** middleware stacks (devtools, immer, persist) break TypeScript inference when applied to the inline pattern. `StateCreator<T>` is Zustand's recommended TypeScript approach and the one the roadmap learning goal explicitly names. Using it consistently from day one means no store needs to be retrofitted later.

**Future note:** when a store needs multiple middleware layers (e.g. `immer` + `devtools`), the type signature becomes `StateCreator<T, [['zustand/immer', never], ['zustand/devtools', never]]>`. Document this pattern in the store file when it first appears so it's clear why the signature looks more complex.

---

### D9 — Zustand devtools middleware included in dev builds only

**Decision:** wrap stores with `devtools` conditionally using `__DEV__`:

```ts
const useAuthStore = create<AuthState>()(
  __DEV__ ? devtools(authSlice, { name: 'AuthStore' }) : authSlice,
);
```

**Why:** devtools adds Redux DevTools Extension support — every action is logged with a name and the before/after state diff. Zero cost in production builds. Invaluable for tracing auth state transitions (`isLoading`, `session`) and GPS accumulation in `routeCoordinates`. The first time a bug hides in a state transition, having named action history saves hours.

**Scope:** apply to all stores. Each store gets a unique `name` label so actions from different stores are identifiable in the DevTools timeline.

**Future note:** in React Native, Redux DevTools requires Flipper (with the React Native plugin) or Reactotron. Document the setup in the project README or a dev-environment guide when the team grows beyond one.

---

### D10 — `useProfileStore` gets a typed stub in this task

**Decision:** create `apps/mobile/lib/store/profile.store.ts` with the correct `ProfileState` type and `null` initial values. No fetch logic. Just the shape.

**Shape:**

| Field       | Type              | Source                   |
| ----------- | ----------------- | ------------------------ |
| `profile`   | `Profile \| null` | `public.profiles` DB row |
| `isLoading` | `boolean`         | fetch in-flight flag     |

Where `Profile` is derived from the generated DB types:

```ts
type Profile = Database['public']['Tables']['profiles']['Row'];
```

**Why:** the root `_layout.tsx` onboarding gate must read `profile.onboarding_completed_at` after `useAuthStore.initialize()` resolves. Without even a stub store, that read has no home and the gate can't be partially wired. A typed stub with no logic costs one file and unblocks Epic 02 from being a fill-in rather than a redesign.

**Future note (Epic 02):** add a `loadProfile()` action that calls `supabase.from('profiles').select().eq('id', user.id).single()` and populates `profile`. Wire it to be called from `useAuthStore`'s `onAuthStateChange` listener after a session is confirmed.
